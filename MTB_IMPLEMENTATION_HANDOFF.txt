A. ARCHITECTURE BOUNDARY
========================
Two scheduling systems live in this repo. This is deliberate and NOT yet resolved.

1. LIVE PRODUCT (serves real users today)
   backend/server.py  +  Mongo collections `visits` / `visit_instances`
   Active Expo routes under frontend/app/(app)/...
   Handles simple baseline-relative schedules only.

2. CANONICAL ENGINE (UCTSM - Universal Clinical Trial Schedule Model)
   backend/app/domain/schedule/   models, timing, condition, conditional,
                                  evaluator, validator, projection
   backend/app/services/          schedule, impact, extraction,
                                  schedule_projection, notification
   backend/app/db/                SQLAlchemy / Postgres
   backend/app/api/uctsm.py       HTTP surface
   frontend/src/features/uctsm/   shared tabular UI

All new requirement work lands in the UCTSM engine. It is NOT yet wired to the live
patient workflow. Convergence plan: UCTSM owns meaning / version / evaluation;
Mongo remains a compatibility operational projection until the bridge and parity
gates in D-1 are complete.

SESSION 9 CHANGED THIS BOUNDARY for NEWLY CREATED trials only. Add Trial now
builds canonical DRAFT schedule versions from the same extraction it already ran,
and routes the sponsor to the UCTSM protocol review screen. Add Patient reads the
approved canonical schedule for its protocol-group fields. The operational Mongo
path is untouched and still serves every existing trial and every visit WRITE.

Still true: DO NOT switch an existing trial's visit READS to UCTSM until D-1
passes parity for that trial. Building a draft is not a cutover - a draft cannot
reach a patient until a person approves it.

B5. Patient schedule-version pinning + amendment workflow  [doc 9]
    app/services/impact_service.py implements preview -> confirm -> reconcile:
      - patient pinned to an immutable approved schedule version
      - preview returns UNCHANGED / ADDED / MOVED / STATUS_CHANGED / CANCELLED /
        PROTECTED and writes nothing
      - proposals carry an expiry AND a SHA-256 input fingerprint; confirmation is
        rejected as STALE if patient inputs or the assignment moved underneath it
      - confirmation writes PatientScheduleAssignment + audit events
      - existing patients are never auto-migrated when a new version is approved

B6. Deterministic reconciliation with protected history  [doc 1 s18-20]
    Stable logical_occurrence_id / logical_key across re-evaluations, so re-running
    recalculates one visit instead of creating duplicates. COMPLETED / MISSED /
    actual-dated occurrences are PROTECTED: dates and statuses carry forward
    untouched while the expected date is still recalculated for deviation analysis.
    idempotency_key prevents duplicate generation runs. Every evaluation is audited.
    TESTS: test_uctsm_impact.py, test_uctsm_workflow.py

B7. Dependency modes  [doc 4]
    NOMINAL: later visits stay on the original timeline when an earlier visit runs
    late. ACTUAL_PREVIOUS_EVENT: dependents recalc from the ACTUAL previous date and
    stay BLOCKED with waiting_for_actual until that actual exists. MANUAL: stays
    WAITING_FOR_ANCHOR until a site-entered date arrives. UNCLEAR: blocked at
    validation, never guessed.
    TEST: backend/tests/test_uctsm_domain.py

B8. Recurrence / open-ended schedules in the canonical engine  [doc 3]
    Recurrence is stored as a RULE and expanded only to an explicit horizon.
    Termination supports COUNT / DATE / EVENT / CONDITION / HORIZON. A termination
    condition that is TRUE but has no effective time returns UNRESOLVED rather than
    a guessed stop date.
    TEST: backend/tests/test_uctsm_domain.py

B9. Activity-level / intra-day timing  [doc 5 s35-47]            <-- session 3
    - New ActivityReference temporal reference: an activity may be timed from
      another activity in the same visit occurrence (dose, infusion end, previous
      sample, arrival).
    - evaluator.evaluate_activities resolves each occurrence's activities:
      applicability, conditions, requiredness, sequence order, planned time,
      activity window, actual time.
    - SAFETY: an activity anchored on another activity resolves ONLY from that
      activity's ACTUAL recorded time. Patient arrival is never a default anchor.
      Unresolved activities return WAITING_FOR_ANCHOR naming what they wait on
      (explanation.waiting_for_activity).
    - Progressive generation: arrival-anchored work resolves once arrival is
      recorded; dose-anchored work waits for the dose time.
    - Correcting a dose time moves pending activities but leaves recorded actual
      times untouched; the expected time is still recalculated for deviation.
    - Recurring visits keep intra-day actuals separated per occurrence index.
    - Persistence: uctsm_patient_activities (materialized day-wise schedule) and
      uctsm_patient_activity_records (append-only; corrections supersede).
    - API: POST /patients/{id}/activities; GET /patients/{id}/schedule returns
      each event's activities.
    TESTS: test_uctsm_activity_timing.py (10), test_uctsm_condition_workflow.py

B10. Conditional / triggered scheduling engine  [doc 2]           <-- session 3
    - app/domain/schedule/conditional.py builds a ConditionalPlan per patient:
      which events are activated, cancelled, or held for manual review, and which
      repeating blocks are paused or stopped. It decides WHAT applies; the
      evaluator decides WHEN.
    - An untriggered conditional visit gets NO date, so it can never become due,
      overdue, or generate a reminder.
    - PENDING_CONFIRMATION does not act: a detected but unconfirmed condition never
      restructures the schedule.
    - REPEAT_EVENT generates repeat-until-resolution occurrences from the condition
      occurrence date and stops at the recorded resolution date.
    - STOP_BLOCK cancels only future occurrences of a repeating block; completed
      cycles are preserved. PAUSE_BLOCK marks future occurrences PAUSED, not
      cancelled. A stop is terminal - a later pause or resume cannot revive it.
    - A condition occurrence date can anchor resulting visits (Anchor gains
      source_condition_code), so "survival follow-up 12 weeks after progression"
      resolves from the confirmed progression date.
    - Conditional definitions carry their own applicability, so an arm-restricted
      rule is not even offered to patients in another arm.
    - MANUAL_REVIEW keeps the event UNRESOLVED with a named reason and no date.
    - Activation is patient-specific: one patient progressing never touches another.
    TEST: backend/tests/test_uctsm_conditional_engine.py (12)

B11. Condition activation as a confirmed, auditable workflow  [doc 2 s10, s34-36]
    Doc 2 is explicit that selecting a condition must not immediately restructure
    the schedule. Condition changes reuse the impact preview -> confirm pipeline:
      - preview evaluates with the proposed condition WITHOUT persisting it, and
        the proposed change is part of the staleness fingerprint
      - confirm persists the transition, then re-evaluates and reconciles
      - reversal writes a CANCELLED row that supersedes the activation rather than
        deleting it, and the wrongly activated pathway returns to inactive
      - every transition writes PATIENT_CONDITION_STATE_CHANGED to the audit log
    API: GET  /patients/{id}/conditions
         POST /patients/{id}/conditions/impact-preview
         POST /schedule-impact-proposals/{id}/confirm | /cancel
    TEST: backend/tests/test_uctsm_condition_workflow.py (6)

B12. Confinement / inpatient episodes  [doc 6]                    <-- session 3
    - A continuous stay is ONE parent episode with child study days, never one
      hospital visit per study day.
    - Study-day dates use clinical day numbering (there is no Day 0), so Day -1 is
      one day before Day 1.
    - Admission, dose, and discharge stay distinct events, so the dosing anchor is
      never replaced by the admission time.
    - Actual admission puts the patient IN_CONFINEMENT; the episode stays open until
      an ACTUAL discharge is recorded. A planned discharge date passing does not
      close it.
    - Planned and actual admission/discharge are kept separate for deviation.
    - A conditional EXTEND_CONFINEMENT moves the expected discharge and marks the
      episode EXTENDED; it never creates a second episode.
    - Episodes respect arm/cohort applicability.
    TEST: backend/tests/test_uctsm_confinement.py (12)

B20. Rolling horizon for open-ended repeats                   <-- session 5
    [doc 3 s2, s4, s7, s8, s36]

    _apply_rolling_horizon in evaluator.py.
    The two halves of this requirement pull against each other, so both are

B21. Pause and resume semantics for a repeating block         <-- session 5
    [doc 3 s19, s20]
    BlockDirective now keeps the ORDERED transition history, not just the latest
    state, because a block that paused and resumed needs the pause interval.
      - occurrences inside the pause are PAUSED, not missed
      - NOMINAL resume: the cadence keeps its original grid; occurrences during
        the hold are simply not made up
      - ACTUAL_RESUME: the cadence restarts from the resume date, shifting later
        occurrences by exactly the days held
      - MANUAL or UNCLEAR: the protocol did not say, so nothing is invented. The
        occurrences after the resume go UNRESOLVED with the reason, for a reviewer
      - a stop stays terminal; a later pause or resume cannot revive it
    TESTS: test_uctsm_rolling_horizon.py (5 of 11)

B22. Protocol-defined unscheduled visits                      <-- session 5
    [doc 10 s13, s14, s15]
    Event.activation = ON_DEMAND, evaluated by _evaluate_on_demand.
    "Unscheduled Visit - may occur at any time for suspected toxicity" is a
    DEFINITION. Treating it as a dated visit produces a reminder nobody
    scheduled and an overdue flag for a visit that was never required, so:
      - the definition evaluates to AVAILABLE_ON_DEMAND, a status distinct from
        both NOT_APPLICABLE and WAITING_FOR_CONDITION, carrying no date
      - deviation reports it as NOT_ASSESSABLE ("never required to occur"),
        never as missed; the projection emits no reminder for it
      - the validator no longer blocks approval on its undated timing, because
        having no computable date IS the requirement here. The inverse mistake -
        an on-demand visit that also has a calculated protocol date - is now
        blocked as CONFLICTING_SOURCE
      - creating one is patient data: it produces a dated occurrence carrying the
        definition's activities, and reaches no other patient and no master
        schedule. Regeneration reproduces it rather than erasing it
      - a reason is mandatory, and a scheduled protocol visit cannot be created
        this way, so a CRC cannot invent a protocol requirement
    API: POST /patients/{id}/unscheduled-visits

B24. Anchor status vocabulary                                 <-- session 5
    [doc 1 s22]
    app/domain/schedule/anchor_status.py (pure) +
    app/services/anchor_status_service.py (reads the stored records).
    NOT_REQUIRED / AWAITING_EVENT / PLANNED / ACTUAL / CONFIRMED / CORRECTED.
    The pair that matters is PLANNED vs ACTUAL. A planned surgery date is not
    evidence surgery happened, so:
      - a PLANNED value never becomes ACTUAL on its own; only a record whose
        source asserts the event occurred does that
      - an unrecognised source type is treated as PLANNED, never as ACTUAL, so a
        new source cannot quietly promote an expectation into a fact
      - AWAITING_EVENT names the event it waits on, which is what makes an
        undated visit explicable instead of broken
      - an unconfirmed candidate is not the anchor's value at all (doc 1 s10, s16)
      - CORRECTED is distinct from CONFIRMED, so a reviewer sees that a confirmed
        date was changed rather than only seeing the new one
      - NOT_REQUIRED is derived: an anchor only referenced by visits this patient
        will not have stops sitting on a site's to-do list. If the patient context
        cannot be built, every anchor is shown rather than hidden - a spurious
        anchor is recoverable, a hidden one leaves a visit undated forever
    API: GET /patients/{id}/anchors
    UI: toAnchorStatusRows
    TESTS: test_uctsm_anchor_status.py (12), test_uctsm_anchor_status_service.py (7),

B26. Patient reassignment through impact preview              <-- session 5
    [doc 8 s22]
    PatientScheduleImpactService.preview/confirm now accept assignment_change.
    Reassigning an arm, cohort, part or substudy changes WHICH visits a patient
    has, so it is exactly the kind of change the master requirement says must be
    confirmed rather than applied:
      - the preview evaluates against a DETACHED copy of the patient, so asking
        the question cannot change the answer. A preview never confirmed leaves
        the patient untouched
      - confirming applies the assignment, regenerates, and audits with the
        previous assignment recorded in `before`
      - the patient's CURRENT assignment is part of the input fingerprint, so a
        proposal confirmed after someone else moved that patient goes STALE
        instead of applying numbers that were computed for a different state
      - values are validated through the same hierarchy rules as enrolment
      - open dimensions (PART / SEQUENCE / SUBSTUDY / COUNTRY) go through
        dimension_values, so no migration is needed per protocol
    API: POST /patients/{id}/assignment/impact-preview, confirmed by the existing
         POST /schedule-impact-proposals/{id}/confirm
    TESTS: test_uctsm_assignment_impact.py (6)

B27. Typed schedule-version comparison                        <-- session 5
    [doc 9 s10]
    app/domain/schedule/diff.py gains ChangeType, Significance and TypedChange
    alongside the existing raw field diff, which is unchanged for callers.
    A raw diff says "these bytes differ". The question a reviewer is answering is
    "does this amendment affect anyone already enrolled?", so every difference is
    classified:
      - visit added / removed / renamed, timing changed, window widened vs
        NARROWED, activity added / removed / changed, applicability, trigger,
        dependency, recurrence, visit mode, anchor added / removed
      - WINDOW_WIDENED and WINDOW_NARROWED are separate types because they are
        not equally safe: nothing already booked can fall outside a WIDER window,
        while narrowing one can put existing bookings out of window
      - a window change is only reported as such when the NOMINAL date did not
        also move; moving the visit itself is a TIMING_CHANGED
      - a rename is ADMINISTRATIVE. Everything else, including any change type
        not on the list, is CLINICAL - an unclassified change is one nobody has
        looked at
      - activities are compared individually, not as one blob, and a regenerated
        UUID is not treated as an amendment
    API: GET /schedule-versions/{left}/diff/{right} now also returns
         typed_changes and clinically_significant_count.
    UI: toScheduleChangeRows, clinical changes sorted first.
    TESTS: test_uctsm_schedule_diff.py (15), uctsm-event-types.test.ts (3)

B28. LLM extraction provider                                  <-- session 6

    app/extraction/llm_client.py (transport), prompts.py (the rules the model is
    held to), claude_provider.py (the provider), runner.py (execution).

    THE DIVISION OF LABOUR IS THE DESIGN:
        the MODEL reads the protocol and produces CLAIMS with citations;
        deterministic code ASSEMBLES those claims into the canonical schedule.
    Assembly is not a second model call. Source traceability has to survive the
    pipeline, and a model asked to emit its own ClaimEvidence will occasionally
    forget one - at which point a schedule looks complete while a reviewer can no
    longer check where a rule came from. Generating traceability mechanically
    from each claim's citations makes that failure impossible rather than rare.

    One focused call per semantic category (18 of them) rather than one enormous
    call, so a bad answer degrades ONE dimension of meaning instead of losing the
    extraction. The document is sent as a cached prefix, so calls after the first
    are cheap.

    WHAT HAPPENS WHEN THE MODEL IS WRONG - the tested part:
      - a claim citing a passage that does not exist is DROPPED with an issue.
        The model only ever sees refs it was given ("e1"), never UUIDs, so it
        cannot invent a citation that resolves
      - a claim naming a visit that was never extracted raises UNRESOLVED_REFERENCE
      - a timing the model expressed wrongly leaves the visit UNRESOLVED rather
        than becoming a near-miss date nobody would question
      - prose instead of JSON becomes an issue, never an empty answer - an empty
        answer is indistinguishable from "the protocol does not say this"
      - a visit with no timing claim gets UNRESOLVED plus an issue naming it, and
        the validator blocks approval. That is the correct outcome
      - an unreachable model produces issues and no events, not a plausible-looking
        empty protocol
    Unstated things stay unstated: no defaulted visit mode, no defaulted
    dependency mode, no invented recurrence maximum.

    Assembly runs in the CONSISTENCY_CHECK node, not the assembly node, because
    the graph collects issues before it collects the schedule - assembling later
    computed the reviewer-facing findings and then discarded them.

    API: POST .../extract-schedule now executes in the background and reports
         provider_configured. A run that cannot start is marked FAILED with the
         reason instead of sitting QUEUED forever.
    CONFIG: ANTHROPIC_API_KEY, UCTSM_EXTRACTION_MODEL (default claude-opus-5).
    TESTS: test_uctsm_llm_extraction.py (24, all offline via a scripted client),
           test_uctsm_unscheduled_api.py (1 API-level)

B31. Condition recurrence and version effective date          <-- session 7
    [doc 2 s14, doc 9 s8]
    ConditionState.RECURRED. A toxicity that came back is not the same clinical
    picture as one occurring for the first time, even though the protocol
    response is identical. So it ACTS exactly like ACTIVE - the same visits are
    generated, anchored on the recurrence's OWN date - but stays distinguishable
    for a reviewer deciding on dose reduction. A RECURRED status at occurrence
    index 0 is refused, because index 0 is the first occurrence.

    ScheduleVersion.effective_from. Approval and effect are different moments. An
    amendment approved today may not apply to new enrolments until a stated date:
      - the approved-schedules listing reports effective_from and in_force
      - ENROLMENT REFUSES a version that has not taken effect, naming the date it
        starts. Silently enrolling onto a future amendment puts a patient on a
        schedule the protocol says does not apply to them
      - NULL keeps the previous behaviour, so every existing row is unchanged

B33. The Mongo cutover: parity gate and date overlay         <-- session 8
    [D-1, the last structural blocker]

    THE PROBLEM. Moving visit reads from the operational store to the engine
    changes what a site sees for patients already enrolled. The ID bridge existed
    (external_trial_id / external_patient_id, migration 0009), but nothing proved
    the two systems agreed, and nothing stopped someone routing reads anyway.

    THE PARITY GATE. app/domain/schedule/parity.py compares one patient's
    schedule across both systems. It is deliberately unforgiving:
      - a visit on one side and not the other is a DIFFERENCE, never an omission.
        Two systems disagreeing about which visits EXIST is the worst failure
        available and the easiest to hide by matching loosely
      - one day of disagreement blocks. There is no tolerance setting, because
        "close enough" is how a protocol window gets missed
      - the engine REFUSING to date a visit legacy did date still blocks. It is
        usually the engine being right - legacy substituted a date where no
        anchor existed - but a site currently sees a date, so a person signs it
        off rather than the system deciding
      - two visits with the same name are reported AMBIGUOUS, never paired by
        position. Pairing by list order is exactly the quiet guess this prevents
      - an empty comparison is NOT_COMPARABLE, not a pass. Nothing to compare
        proves nothing

    THE CUTOVER RULE. Trial.schedule_read_mode defaults to LEGACY and moves to
    ENGINE only when EVERY patient pinned to a version has a MATCHING recorded
    run against THAT version. No override, no force flag. A trial where nine
    patients matched and the tenth was never checked is not ready - the tenth is
    the one who ends up on the wrong day. A new schedule version invalidates
    earlier runs rather than carrying an old approval forward.

    Moving BACK to LEGACY needs no gate at all, and that asymmetry is tested.
    Reversing a cutover must never be harder than making one.

    THE OVERLAY - why this is survivable. app/services/operational_read.py
    overlays DATES ONLY. A visit_instance carries comments, tasks, workflow
    state, who completed it; the engine has no equivalent and should not acquire
    one. So:
      - nothing is created and nothing is deleted. A read cannot lose a site's
        comment thread, whatever the engine thinks
      - reverting is instant and total, because the original dates were never
        overwritten
      - a visit the engine cannot date KEEPS its operational date and is flagged.
        Blanking it would drop a visit from a site's list on a disagreement
      - an engine visit with no operational document is REPORTED, not invented.
        Creating one on read would give it no workflow history and no audit trail

    LIVE WIRING. server.py gained one helper and two call sites (/visits/mine and
    /patients/{id}/visits) - 59 added lines, 0 removed. It returns rows untouched
    for any trial not cut over, which today is all of them, and also on any
    failure: a schedule read must not break because the canonical side is down.

    API: POST /patients/{id}/parity-check, GET+POST /trials/{id}/read-mode
    DB: migration 20260901_0013 (schedule_read_mode, uctsm_parity_runs)
    UI: toParityRows, describeReadiness
    TESTS: test_uctsm_parity.py (15), test_uctsm_cutover.py (18),
           test_uctsm_unscheduled_api.py (4 API-level),
           uctsm-review-surfaces.test.ts (6)

    NOT DONE, and deliberately: no trial has been cut over. The mechanism is

B34. The last small requirement gaps                          <-- session 8
    [doc 1 s21, doc 5 s26, doc 10 s3]

    ANCHOR-CHANGE AUDIT (doc 1 s21). Confirming an anchor recorded only the new
    value. "The anchor is 03-Nov" does not tell a reviewer that every dependent
    visit moved by four days, so the audit now carries the value it REPLACED, and
    a correction emits PATIENT_ANCHOR_CHANGED while a first recording emits
    PATIENT_ANCHOR_CONFIRMED - two different events a reviewer can tell apart
    while scanning a trail.

    VISIT COMPLETION (doc 5 s26). "N of M required assessments complete", with
    the outstanding ones named. OPTIONAL assessments are excluded from the
    denominator on purpose: counting them makes a visit where everything required
    was done read as incomplete, and a CRC chasing a false gap stops trusting the
    number.

    EVENT TYPE TAXONOMY (doc 10 s3). An event type outside the known set is a
    non-blocking WARNING. Blocking would stop real work over vocabulary; treating
    an unknown type as an ordinary site visit could tell a patient to travel.
    Generic labels (VISIT, CONTACT, OTHER) are accepted because they are
    presentation-SAFE - they promise nothing about how the patient attends, which
    the visit-mode fields decide separately.

  THE ONE CAVEAT WORTH READING TWICE
  Every percentage in this file measures whether a REQUIREMENT IS IMPLEMENTED,
  not whether the system is correct on a real protocol. Those are different
  claims. The extraction provider is proven to fail safely - a bad citation is
  dropped, an unparseable timing stays unresolved, an unreachable model produces
  issues rather than an empty schedule. It is NOT proven to read a real
  schedule-of-assessments table correctly, because no one has scored it against
  one. Until that exists, treat every extracted schedule as a draft that a human
  must review line by line, which is what the approval gate already enforces.
